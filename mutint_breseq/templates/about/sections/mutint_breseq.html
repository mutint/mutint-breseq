Run breseq from the browser. Drop an experiment's FASTQ read files on /breseq/ or name them by SRA accession — a run, a sample, an experiment or a study, fetched from ENA's mirror — name the sample, and breseq is run in the background against the reference genome that experiment already holds. What it produces is imported exactly as a breseq folder dropped on the Add Data page would be, so the sample that appears is indistinguishable from one analyzed elsewhere and uploaded.

One launch is one sample: every file dropped or fetched is that sample's reads — both mates of a pair, or several lanes — unless the input type says each file set and each accession is a sample of its own. The single arguments box is passed through to breseq as typed, so anything its own documentation describes is available; the processor count defaults to every core on the machine unless you set it yourself. Reads are adapter-trimmed with fastp first unless you deselect the box, pairs together and long reads left alone, and pair means what it means to breseq.

The work runs on the task queue rather than in the request, because a real genome takes hours. That means a worker has to be running — ./mutint db_worker — and the run list says so when nothing has picked a job up. After a successful import only breseq's own HTML report is kept: the reads are large, and everything else worth having is already in the store under the sample.
