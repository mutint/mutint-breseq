# External (non-Python) tools this component needs, as conda package specs -- one per line,
# `#` comments ignored. The entry script collects these from every component the same way it
# collects requirements.txt, and installs them into env/tools with micromamba. Code finds
# them through mutint_common.tools.tool_path(), which falls back to PATH.
#
# breseq itself, which mutint_breseq/tasks.py runs on the reads dropped on /breseq/.
#
# **The channel is written into the spec, and has to be.** breseq-prerelease is published from
# the lab's own channel rather than to bioconda, and the entry script's channel list is
# `-c conda-forge -c bioconda` -- three byte-identical copies of a file with no tests, which
# is not a thing to edit for one package. micromamba takes `channel::package` with a URL
# channel, so the dependency declares its own source and the entry scripts stay untouched.
# Its dependencies (bowtie2, samtools, htslib, gnuplot, phylip) resolve from bioconda, which
# is already on that list.
#
# Prerelease rather than the stable bioconda `breseq`, because this tracks breseq's master.
#
# **Pinned by build string, and copy it exactly as the channel publishes it.** Every build
# reports a version derived from git -- `0.40.1.dev425+g9aab25c1` -- and publishes it with the
# short hash as its *build*, so `=*=<build>` names exactly one artifact.
#
# **The build is not always just the hash**: a rebuild of the same commit gets a `_N` suffix,
# and the current one is `g67b6320e_2` -- a `_2`, so copying the hash or guessing `_1` both
# name nothing. `dev424` is published twice, as `gab1f4511` and
# `gab1f4511_1`, which is what makes this worth stating -- the hash alone is not a spec. A
# build string that matches nothing does not degrade to something older, it fails the *whole*
# tools solve, and with it `./mutint start`: measured, `=*=g9aab25c1` (no suffix) stops with
# `does not exist (perhaps a typo or a missing channel)`. Read the build off the channel's
# repodata rather than off the version string:
#
#     curl -s https://barricklab.github.io/conda/osx-arm64/repodata.json
#
# and check the platform you are *not* on as well -- one solve covers every component, and CI
# runs on linux-64. Dry-running that solve **from macOS needs
# `CONDA_OVERRIDE_GLIBC=2.28 CONDA_OVERRIDE_LINUX=5.10`**: without them micromamba cannot
# detect the target's virtual packages and refuses with `__glibc >=2.17 ... is missing on the
# system`, which reads exactly like the package being unavailable for linux-64 and is not.
#
# `=<version>=<build>` would pin the same artifact and is deliberately not used: it is two
# coupled tokens that must be edited together and mean nothing if they disagree.
#
# **A floor, not a preference: gf7100f9a.** That is the build `--max-evidence-items` and
# `--max-percent-divergence` arrived in, and `runner.build_argv` puts both on every command
# line by default (see `DIVERGENCE_DEFAULTS` there). An older breseq rejects the flags, so
# every run would fail at the preflight -- which is the loud failure to want, but it means
# moving the pin backwards past gf7100f9a is not a thing that works. Before that the floor
# was g23736ada, where `--dry-run` arrived; `views.launch` and `tasks.run_breseq` both still
# gate a run on it.
#
# g23736ada also predicts CN, DP, MP and PD evidence by default, where those were opt-in.
# The old `--predict-*` flags are still accepted and now do nothing, and the old
# `--skip-*-prediction` spellings still work, so arguments saved on existing runs keep
# working. CN wants `CNery` on PATH and is skipped with a warning without it, which is why
# nothing is added below.
#
# g9aab25c1 calls copy number on a continuous grid in polymorphism mode. It changes what CN
# evidence a polymorphic run reports; it changes no flag, so nothing in this plugin had to
# move with it.
#
# **Read the build off the channel, and defeat the cache while you do it.** GitHub Pages
# serves this channel with `cache-control: max-age=600`, so a plain `curl` can hand back an
# index that predates a build published minutes ago -- which happened while pinning ge1bbc07f,
# and read as "there is no new version". Send `Cache-Control: no-cache` and a cache-busting
# query. And **`cnery-prerelease` is `noarch`**: it is in neither `osx-arm64/repodata.json`
# nor `linux-64/repodata.json`, so looking for it there finds nothing and proves nothing.
#
# gf7100f9a turns breseq's long-standing divergence *warning* into an optional hard stop:
# `--max-evidence-items` and `--max-percent-divergence`, both off in breseq itself. This
# plugin turns them on (5000 items, 1.0%), because a person who drops reads against the wrong
# reference would otherwise get a run that spends hours annotating hundreds of thousands of
# spurious mutations and then imports every one of them.
#
# **g67b6320e, the build pinned below, is where copy-number prediction and `-c` can coexist.**
# breseq depends on `cnery-prerelease` now and *calls* it, so CN prediction runs on every
# ordinary run rather than being skipped for want of the tool. Two things had to land together
# for that to be usable here, and the build in between shows why this list is checked by
# running it rather than by reading a changelog:
#
#   * ge1bbc07f calls `CNery --group-table <tsv> -o <dir>`, and CNery leaves the
#     origin/terminus columns **empty** for a sequence in a `-c` group -- it does not measure
#     GC skew for one. breseq's `read_cnery_windows` read those with `from_string<double>`, so
#     every run using `-c` died on `Attempt to convert empty string`, hours in, with no
#     `output.gd` and no `summary.json`. Measured here against the same inputs that pass on
#     gf7100f9a and on g67b6320e; `-r` alone was unaffected, which is why it is easy to miss.
#   * ge1bbc07f also declared `cnery-prerelease >=0.1.0.dev122`, which the *older* dev124
#     satisfies -- so a fresh solve worked and an **existing** `env/tools` kept dev124 and
#     failed with `CNery: error: unrecognized arguments: --group-table`. That is the shape to
#     watch for: a constraint loose enough that only a prefix built from scratch is correct,
#     which is every developer's machine and, through `restore-keys`, CI. g67b6320e tightens
#     it to `>=0.1.0.dev127`, and installing the spec below into a prefix holding dev124 does
#     upgrade it -- verified, which is why no `cnery-prerelease` line is needed here.
#
# `-c` is not incidental to this plugin: `runner.reference_arguments` emits it for any
# experiment whose contigs carry the Contig role, so "CN evidence" and "draft assembly" are a
# combination MutInt produces by default. A breseq that cannot do both is not one to pin.
#
# It was unpinned, on the reasoning that a version cannot distinguish these builds. That is
# true of the version and not of the build, and unpinned meant a checkout tracked master on a
# fresh `env/tools` and then never moved again: the spec was already satisfied, so micromamba
# was never asked. The entry script fingerprints the *spec list* (`env/tools/.installed`), so
# editing the build below is what makes the next `./mutint start` install the new breseq --
# here, and on an installation, through `/update/`, which is applied before that fingerprint
# is read.
#
# **Moving it backwards can fail to solve** in an existing prefix, where breseq's own
# dependencies are already installed at versions a much older build will not take. Measured:
# `=*=gc6cf9186` (44 commits back) refuses with `conflicts with any installable versions`.
# `rm -rf env/tools` is the way through, and is safe -- the tools live in `env/`, the database
# and the file store in `data/`.
#
# **breseq shells out to its own toolchain by bare name** -- bowtie2, samtools, gnuplot --
# so `tool_path("breseq")` is not sufficient on its own: the subprocess needs env/tools/bin
# on PATH or breseq stops with `Required executable "bowtie2" not found`, having exited 0.
# mutint_breseq/runner.py `tool_environment()` is what builds that PATH.
https://barricklab.github.io/conda/::breseq-prerelease=*=g67b6320e_2
